## 1. Version numbers

Keep it boring:

- `version` in `Cargo.toml` is the only place the number lives. It's still
  `0.1.0` and has never been bumped.
- Semantic versions. First public download is `0.2.0`. Bump the middle number
  for new features, the last number for fix-only releases. `1.0.0` when you'd
  tell a stranger to use it.
- Every release gets a git tag `v0.2.0` and a section in `CHANGELOG.md`.
- MSIX wants four numbers and the Store needs the last one to be 0, so
  `0.2.3` becomes `0.2.3.0`. The release job does that conversion, you never
  type it.
- Builds that aren't from a tag show `0.2.0+abc1234` (short commit) in Help >
  About and `--version`, so bug reports say which build it was.

To cut a release: bump `Cargo.toml`, add the changelog section, commit, then
start the release workflow (next section). No other steps.

## 2. Releases on GitHub Actions

The repo is public, so standard GitHub-hosted runners (Windows, Linux and
macOS) cost nothing. The limit that matters is that you don't want a release
every time something merges, so **releases never run on push to main**. CI
keeps running on every push like now; releasing is a separate workflow:

```yaml
# .github/workflows/release.yml (sketch)
on:
  workflow_dispatch:      # "Run workflow" button on the Actions tab
    inputs:
      draft:
        type: boolean
        default: true
```

You press **Run workflow** on the Actions tab (or run
`gh workflow run release.yml`). The job reads the version from `Cargo.toml`,
refuses to run if tag `vX.Y.Z` already exists, builds everything below,
creates the tag and a **draft** GitHub Release with the files attached. You
look it over and click Publish. Nothing goes public by accident.

What gets built:

| Platform | Files | Notes |
| --- | --- | --- |
| Windows | `buttonscli-0.2.0-windows-x64.zip` (plain exe) | Yes, ship the plain exe. Terminal people like portable zips. It's unsigned, so SmartScreen will warn on first run until it has a reputation. |
| Windows | `buttonscli-0.2.0.msix` | For the Store only. You upload it to Partner Center by hand. The Store signs it. |
| Linux | `.tar.gz`, `.AppImage`, `.deb`, `.rpm` | AppImage runs on almost any distro without installing. `.deb`/`.rpm` are cheap to add with `cargo-packager` (or `cargo-deb` / `cargo-generate-rpm`). |
| Linux | Flatpak | **Skip for now.** Flatpak's sandbox hides the host's shells, so a terminal app has to tunnel every shell through `flatpak-spawn --host`. That's real work and a lot of Flathub review back and forth. Revisit later. |
| macOS | `ButtonsCLI.app` in a `.dmg` (universal: Intel + Apple Silicon) | Unsigned at first, so people right-click > Open the first time. Notarization needs the $99/year Apple developer account; worth it once Mac users show up. Mac interaction hasn't been tested yet. |

Tools: `cargo-packager` makes the `.app`/`.dmg`, AppImage and `.deb` from one
config in `Cargo.toml`. MSIX uses `makeappx.exe` from the Windows SDK, which
is already on the `windows-latest` runner. Also attach `SHA256SUMS.txt`.

Skip a separate MSI/EXE installer for now. Without a paid code-signing
certificate it gets the same SmartScreen warnings as the zip, and the Store
covers the "proper install" case on Windows.

### Updates

- **Store build:** the Store updates it. The app must not update itself.
  Build it with a `store` cargo feature that removes the update check entirely.
- **Zip / Linux / Mac builds:** start with a "version 0.3.0 is out" notice that
  links to the release page, checked at most once a day, with a setting to turn
  it off. Proper download-and-restart updates come later using the signed
  manifest code already in `src/distribution.rs`.

## 3. Microsoft Store checklist

Done: developer account, app name reserved, Hyper-V VM with the MSIX packaging
tools.

Still to do, roughly in order:

1. **Copy the identity values.** Partner Center > your app > Product
   management > Product identity: `Package/Identity/Name`,
   `Package/Identity/Publisher` (`CN=...`) and `PublisherDisplayName`. They go
   into the manifest exactly as shown.
2. **Write `packaging/msix/AppxManifest.xml`.** Things it needs:
   - `TargetDeviceFamily Name="Windows.Desktop" MinVersion="10.0.17763.0"`
     (ConPTY needs Windows 10 1809 or newer).
   - `EntryPoint="Windows.FullTrustApplication"` and the `runFullTrust`
     capability. It's a restricted capability, so the submission asks why.
     Answer: it's a terminal and has to launch the user's shells.
   - An app execution alias (`uap5:AppExecutionAlias`) so typing `buttonscli`
     in a terminal still works after a Store install.
   - A `<Resource Language="..."/>` line for each UI language (see section 6).
   - Logos: `StoreLogo` (50x50), `Square44x44Logo`, `Square150x150Logo`,
     `Wide310x150Logo`. Make them from the existing icon; scale-200 versions
     look better on high-DPI screens.
3. **Add a `store` build feature** that turns off the update check (section 2).
4. **Package it:** `makeappx pack /d <folder> /p buttonscli.msix`. Add this to
   the release workflow once it works by hand.
5. **Test it in the Hyper-V VM** (clean Windows, which is the point of the VM):
   - Sign with a throwaway self-signed cert whose subject matches the
     `Publisher` value, trust the cert, and install with `Add-AppxPackage`.
   - Check that it starts. **Important: Hyper-V VMs usually have no real GPU.**
     If wgpu can't find an adapter there, the app may fail to open, and Store
     testers may hit the same thing. It needs to fall back to software
     rendering (WARP) instead of crashing. Check this before submitting.
   - Shells start (PowerShell, CMD, WSL if installed), settings land in
     `%USERPROFILE%\.buttonscli-native`, the `buttonscli` alias works, and
     uninstall works. Note: uninstalling won't delete `~/.buttonscli-native`,
     which is normal for apps that keep settings in the user folder.
   - Run the **Windows App Certification Kit** (WACK) on the `.msix`. It's the
     same automated checks the Store runs first.
6. **Privacy policy URL.** Required, since the app goes online (AI providers
   with the user's own key, optional account features). Turn
   `docs/PRIVACY-AND-FEEDBACK.md` into a plain page on buttonscli.com/privacy.
7. **Fill in the submission:** pricing (free) and markets, category (Developer
   tools), the age rating questionnaire, store listing (description, at least
   one screenshot (you have good ones), search terms), and certification notes:
   "Terminal app that launches the user's own shells. AI features are optional
   and use the user's own API key. No sign-in needed to test."
8. **Submit.** Certification usually takes a few days. For updates later: bump
   the version, build a new `.msix`, start a new submission with it.

Policy things to read once before submitting: the Store Policies sections on
apps that update themselves and on "dynamic code". AI-written shaders are data
compiled by the GPU driver, not app code, and running commands is what a
terminal is for, but it's worth mentioning both in the certification notes so
nobody's surprised.

## 4. Metrics (installs / "does anyone use it")

**The Store already does this, no code needed.** For MSIX apps Partner Center
shows installs and page views (Acquisitions report) and daily/monthly active
users, sessions and which versions people run (Usage report).

For the zip/Linux/Mac downloads, GitHub counts downloads per release file
(visible through `gh release view` or the API). Rough, but free and needs no
code.

Recommendation: **add no telemetry to the app.** If you ever want more, the
lightest honest option is an opt-in "count me" checkbox that sends one request
a day with only the app version and OS, no ID. It has to go in the privacy
policy, and the Store build doesn't need it at all.

## 5. Security scan

### What's already in good shape

- Agent control API: only listens on `127.0.0.1`, needs a random token
  (compared in constant time), rejects browser `Origin` headers and wrong
  `Host` headers (blocks DNS rebinding), connection file is owner-only on
  Linux/macOS.
- API keys live in the OS credential store, not in settings files. Provider
  URLs can't contain usernames, passwords or query strings.
- Links from terminal output only open `http(s)`/`mailto`. The online guide
  only loads from `https://buttonscli.com/dsp/...`.
- AI shader code is checked by the same validator as hand-written code before
  it runs, and the shader language here has no loops, so a generated shader
  can't hang the GPU.
- The only `node` and `powershell` launches outside the user's own shells are
  in tests. The app itself runs `explorer`/`xdg-open`/`open` (to show a folder)
  and `wsl --list`, with fixed arguments.
- HTTPS uses rustls, not OpenSSL.

### Things to fix

1. **Dependency advisories (`cargo audit`: 12 found).**
   - `rustls` 0.23.45 (4 advisories), `rustls-webpki` 0.103.15,
     `webpki-roots` 1.0.9, `ctutils` 0.4.2: all fixed by a normal
     `cargo update -p rustls -p rustls-webpki -p webpki-roots -p ctutils`.
     No code changes expected.
   - `zip` 7.2.0 (3 advisories about `extract()` and symlinks): the app never
     calls `extract()`, it reads entries itself in `src/distribution.rs`, so
     these don't hit it today. Still upgrade to `zip` 9 before the updater
     ships; it's a major version, so it may need small code changes.
   - `quick-xml` 0.30.0 (2): only pulled in by Linux Wayland build tooling,
     reading XML files that ship with the library. Low risk; goes away when
     the windowing crates update.
   - Warnings, not vulnerabilities: `ttf-parser` and `paste` unmaintained,
     `clipboard-win` version yanked, a `tokio` soundness note, and some
     Linux-only `zbus` crates. Watch, don't act yet.
   - Add `cargo audit` (or `cargo deny`) to CI so new advisories show up on
     their own.
2. **Plain `http://` provider URLs are allowed for any host.** If someone types
   `http://` for a remote provider, their API key goes over the network
   unencrypted. Fix: allow `http://` only for `localhost`/`127.0.0.1` and
   private LAN addresses (Ollama, LM Studio), require `https://` for everything
   else, and show a short warning for LAN `http`.
3. **Software rendering fallback** (see Store checklist step 5). A crash on
   launch in a GPU-less VM is the most likely way to fail certification.
4. Not reviewed this round: the 10 `unsafe` blocks (Windows API calls) and the
   vendored terminal forks. Worth one careful read before 1.0.

Store-wise, the automated part is WACK plus a malware scan. Rust's Windows
builds already turn on ASLR and DEP by default.

## 6. Languages

The app already has **21 languages** you can pick: English, Spanish,
Simplified and Traditional Chinese, French, Japanese, Hindi, German,
Portuguese (Brazil), Italian, Russian, Ukrainian, Korean, Arabic, Turkish,
Polish, Dutch, Swedish, Danish, Finnish and Norwegian.

How the Store decides: languages declared in the package manifest show up as
supported languages. You can also add store listings (description and
screenshots) in extra languages through **Manage additional languages** in
Partner Center. So to show up in all 21, declare all 21 in the manifest and
write a listing for each. The listing text is the bigger job.

What's missing inside the app (from `scripts/audit-i18n.py`, a rough count):

- 826 strings are translated into all 21 languages, with no broken
  placeholders.
- About **154 strings are marked for translation but have no translations**,
  plus roughly **90-140 more hard-coded English strings** in buttons and
  labels. Most are the newer screens: shaders and AI shader generation, AI
  models, saved tab groups, the profile switcher, and parts of Settings.
- **Arabic and Hindi probably don't display correctly.** egui doesn't do
  right-to-left layout or complex text shaping, so Arabic letters don't join
  and Hindi conjuncts break. Either leave those two out of the Store manifest
  until that's fixed, or test them carefully first.

Languages worth adding later because they're big Store markets: Indonesian,
Vietnamese, Czech, Thai, Hungarian, Romanian and Greek. Thai would need testing too, since its
marks stack in ways egui may not position well.

## 7. Tab colors (done)

What's wrong now: every tab shown in a pane gets the same two theme accents,
alternating (pane 1 and 3 match, 2 and 4 match). The keyboard-focus tab only
differs by a slightly different fill and a 2 px border instead of 1 px, and
hovering a pane also gives its tab a 2 px border. So "which one gets my
typing" is easy to miss, especially next to a hovered tab.

Idea:

1. **One color per pane slot**, not two alternating. A fixed set of 10
   distinct colors (pane 1 = blue, 2 = orange, 3 = green, ...), chosen to work
   on dark and light themes and for common color blindness. The tab, the pane
   border and the hover label for a pane all use that pane's color. Settings
   option: "Pane colors: Theme accents (old look) / Distinct colors / Custom".
2. **Keyboard focus gets a solid tab**: the tab fills with its pane color, the
   text flips to black or white for contrast, and a small keyboard mark
   (`⌨`) sits before the name. Displayed-but-not-focused tabs keep a dark fill
   with a colored left stripe and colored text. Tabs not on screen stay plain
   and muted.
3. **Hover never looks like focus**: hover just brightens the fill a bit, no
   thicker border.
4. The focused pane's border matches: thicker and in the same solid color.
   Other panes get a thin border in their own color.
5. When the app window isn't in front, dim the focused tab a little so it's
   clear typing won't go there right now.

That keeps the current "pane numbers match tabs" behavior, it just makes
"focus" its own unmistakable look instead of a 1 px difference. I'd mock it up
as a screenshot before changing code.

## 8. Shader controls and the preview bug

### The preview/terminal mismatch bug (fixed)

What you saw: after a long session of generating shaders and messing with the
UI, clicking one of four results put a different shader on the terminals than
the one in its small preview.

Cause: the GPU side keeps at most 32 compiled custom shaders and drops the one
used longest ago when it needs room. It decides "longest ago" with egui's frame
counter, but **each window has its own counter**. The main window redraws
constantly (animated shaders), so its numbers are always far bigger than the
detached Settings window's. Effects:

- Shaders shown in terminals (main window) look "recent" forever and are never
  dropped. After lots of generating and clicking results, they fill most of
  the 32 slots.
- The Settings window's previews always look oldest, so they keep pushing each
  other out, sometimes within the same frame.
- When a preview's shader was pushed out, the draw code silently falls back to
  the **built-in preset shader** (whatever the Style dropdown says) instead of
  the AI code. So the small preview showed a preset, while clicking it put
  the real AI shader on the terminals. The same mix-up can blank a preview
  (the per-pane buffer cache uses the same counter), and it recompiles shaders
  every frame, which costs time.

That matches "only after a lot of use" and "Settings detached". The earlier
log for today mentions this cache as a possible problem; it turns out to be a
real one.

Fix (small, two files):

1. Use one counter shared by all windows (kept in the shader cache itself) for
   both caches in `shader_background.rs`, and the same in `analog_static.rs`.
2. If a custom shader isn't in the cache at draw time, draw nothing rather than
   the preset, so a preview can never show the wrong shader.
3. A unit test for the cache with two windows' worth of draws.

Two smaller reasons a preview can look different from the terminals, by
design: previews bump strength up to 0.45 when the theme's is lower, and
terminals use their own theme's colors for `c1`-`c3`. The first one goes away
with the strength change below.

### Letting you control the limits

Current hard limits: strength 0-0.65 (also capped again inside the shader),
speed 0-2, scale 0.25-4, 1-6 AI versions, 4 sliders per shader with values
between -100 and 100, 4 KB of code, 2,000 characters of prompt.

Plan:

1. **Strength up to 1.0**, raise the cap inside the shader to match, and add a
   **Text readability** slider that dims the shader behind text (0 = raw
   shader, 1 = today's look). Strength alone at 1.0 can make text unreadable,
   which is why the 0.65 cap exists; the readability slider keeps that choice
   with you instead of hard-coded. Default stays where it is now.
2. **Speed up to 10** and **scale 0.1-10**, with a "fine/wide" toggle on the
   sliders so small values stay easy to set. Existing themes load unchanged
   (they're inside the new ranges).
3. **More AI versions:** up to 12, with new creative directions (Retro,
   Minimal, Psychedelic, Nature, Sci-fi, Glitch) added to the six that exist.
   Show an estimate like "12 versions = 24-36 model calls" next to the
   slider, since every version costs money with paid models.
4. **Sliders per shader: 4 to 8.** Needs one more `vec4` in the GPU uniform
   buffer; small change.
5. **Preview the real strength.** Remove the 0.45 bump in result previews so
   what you see is what the terminals get.
6. Older builds clamp strength, speed and scale back into the old ranges, so
   themes saved with the new limits still open there, just toned down. A shader
   with more than 4 sliders would be dropped by older builds, though, so only
   save more than 4 when you need them.
